=== PAGE: Master Plan & Feature Specification ===
THE authoritative implementation plan for StratForge v1. Every architecture section and every feature being added, specified in detail: purpose, spec, guardrails, acceptance conditions, and the phase where it lands. Full detail lives here in Notion (source of truth); the repo docs/ folder mirrors this page as each phase ships.
0. Purpose & guiding principles
User requirements locked into this plan: (1) the bot must never cause a loss greater than 5% of the investment; (2) maximize profit within that guard; (3) when a trade closes, the bot automatically rotates to the next best strategy; (4) AI / agent API integrations (OpenCode, Claude, etc.) are part of the design.
Guardrail #0 — honest framing: a literal never-lose-more-than-5% cannot be guaranteed in live crypto (gap moves, flash crashes, exchange outages exceed any stop). StratForge builds defense-in-depth so exceeding ~5% requires a tail event, plus a HARD equity circuit breaker at -5% that flattens everything and halts trading. The 5% line is the backstop, not the plan.
Principle 1 — capital protection outranks action: breaker > daily limit > strategy budgets > trade selection > rotation. A lower layer may only be overridden by a higher one.
Principle 2 — money path is deterministic: orders are placed only by deterministic engines after risk gates. AI/ML inform signals, regime and proposals; they never execute.
Principle 3 — paper/testnet-first: nothing touches real money until validated on testnet AND by backtest gates; canary then promote.
Principle 4 — compute once in the data plane: one MarketDataProducer ingests and aggregates; every consumer receives the same clean series (Redis Streams fan-out).
Principle 5 — account isolation: one leveraged/futures account per bot, never shared across bots (freqtrade rule). Spot balances pooled only with explicit per-bot budgets.
Principle 6 — test-first: every gate is a machine-checked test (unit + integration + CI), never a convention. If it cannot be tested, it does not ship.
1. Feature register — how to read this document
[v1] = core MVP feature, built and tested in Phases 0–8.
[later] = accepted backlog; architecture already accommodates it; not in the MVP.
[res] = research item studied but not yet committed to the design.
Every feature is specified as: purpose → spec → guardrails → acceptance conditions → phase. Acceptance conditions are the tests that prove the feature.
2. Core runtime
2.1 Asyncio event bus
Purpose: decouple producers (data, orders, risk) from consumers (strategies, executors, dashboard feed).
Spec: typed async events: CandleNew, SignalGenerated, OrderAccepted/Rejected/Filled, TradeClosed, PositionChanged, RiskEvent, RegimeChanged, ConfigReloaded. One event loop per worker; handlers registered by topic; bounded queues with slow-consumer policy — the money path never blocks more than one tick.
Guardrails: no handler blocks the loop >1s; risk and kill-switch paths are highest priority; every event carries an immutable monotonic sequence for replay/debug.
Acceptance: unit test — event emitted once, delivered to all subscribers, order preserved per topic; slow consumer does not stall the loop.
Phase: v1 — Phase 1. ✅ SHIPPED (commit 899e8e8, 2026-09-22)
2.2 Loop, scheduler & lifecycle
Spec: per-bot MainLoop: 1s data tick, 5s decision tick; scheduler runs periodic jobs (balance refresh, risk re-check, funding check, heartbeat) with jitter and misfire handling; graceful stop drains in-flight orders (flat-then-exit, max 60s).
Guardrails: risk re-check runs every tick regardless of strategy state; a crashed job cannot suppress the next run; startup asserts NTP clock skew < 500ms and fails closed.
Acceptance: FakeExchange integration test — loop ticks, schedule executes, graceful shutdown flattens open positions.
Phase: v1 — Phase 1. ✅ SHIPPED (commit 899e8e8, 2026-09-22)
2.3 Configuration
Spec: pydantic-settings; layered: defaults → config files → DB configs table → env overrides. Validated on load and reload. Secrets referenced by vault key, never inline. Hot-reload (REST + /reload_config) applies trading-free changes live; risk-critical params need explicit approval.
Acceptance: invalid config rejected with precise errors; hot-reload applies param change to a running worker; risk-critical values cannot be hot-reloaded without approval.
Phase: v1 — Phase 1. ✅ SHIPPED (commit 899e8e8, 2026-09-22)
2.4 Observability
Spec: structlog JSON logging with correlation ids per trade/rotation; log rotation + journald transport; heartbeat records (worker id, state, last tick, equity) every 5s; counters for events/orders/risk actions exposed for later Prometheus. Secrets redacted at the emitter.
2.5 Startup integrity
Spec: startup: unlock vault → verify clock skew → connect DB (migrations present) → connect Redis → connect exchange (testnet first) → load strategy_state → resume or start clean. Any failure aborts with a precise error; never retries into a half-state.
3. Data plane
3.1 MarketDataProducer & Redis Streams
Purpose: ingest once, fan out many — all consumers share identical cleaned market data.
Spec: one producer per market (spot, futures) consumes WS + REST, normalizes, aggregates OHLCV, publishes to Redis Streams (stream per instrument+timeframe). Consumers use consumer groups; producer is the only writer of raw market data.
Guardrails: producer restart is idempotent on exchange event ids (no gaps/duplicates); consumers replay from last ack; stream retention ≥ 7 days of ticks.
Acceptance: integration test — two consumers get identical series; crash + restart yields gapless resume against a recorded exchange fixture.
Phase: v1 — Phase 2.
3.2 Binance adapters (spot + USDT-M futures)
Spec: REST + WebSocket adapters for spot and USDT-M perpetuals. Capability flags per market (market orders, shorting, leverage tiers, lot size, min notional, fee schedule). Rate-limit budget tracking (weight/minute) with priority lanes; risk/kill-switch calls preempt. Consumes Binance system status; pauses new entries during maintenance windows. Futures adapter exposes the funding-rate feed for the DCA funding guard.
Guardrails: private endpoints callable only with the owning bot's vault keys; every mutation carries an idempotent clientOrderId; exponential-backoff retries; never retry a non-idempotent call.
Acceptance: recorded-payload fixture tests (no network in CI); rate-limit lane-priority test; mid-request disconnection reconstruction.
3.3 OHLCV correctness rules
Completed candles only: strategies never see the in-progress candle — closed-bar (t-1) policy enforced in the aggregator and tested (repainting guard).
Missing-candle fillup: after downtime, empty candles filled with previous close, volume 0, flagged; stale candles are never trade inputs.
Price-jump monitor: gap > 30% flags the instrument degraded (halt/delisting risk); degraded instruments are excluded from new entries.
Aggregation: 1m base from WS trades + periodic REST verification; higher timeframes aligned strictly to exchange boundaries.
Acceptance: unit tests — incomplete candle withheld; gap-filled series matches fixture; price-jump fixture flags correctly.
3.4 Backfill & data integrity
Spec: bulk historical download from data.binance.vision (spot + futures) with per-file SHA-256 checksum before load; daily incremental backfill; SQLite dev fallback on small windows.
Acceptance: tampered archive rejected; backfilled series reconciles with live series at the seam (no lookahead join).
3.5 Derivatives data
Funding rate history stored from v1 (hypertable) — required by the DCA funding guard and fee modeling.
Open interest & liquidation data [later] — schema reserved, ingestion later.
4. Storage
4.1 Schema (SQLAlchemy models, Alembic-managed)
instruments — symbol, market (spot/futures), base/quote, lot size, min notional, leverage tiers, capability flags, degraded flag.
candles — hypertable (time, instrument_id, timeframe, OHLCV) with continuous aggregates; unique (instrument, timeframe, time).
funding_rates — per instrument, timestamp, rate.
orders — every attempt incl. rejected; clientOrderId unique (idempotency); status history.
trades / fills — executed fills with fees (fee currency, BNB discount) and slippage vs reference.
positions — open/liquidated: entry/exit, mark, liq price, leverage, margin mode.
equity_snapshots — time-series equity (spot + futures margin MTM); feeds the breaker and drawdown gauge.
signals — every emitted signal (strategy, instrument, direction, strength, params, regime at time).
regime_snapshots — regime id, confidence, horizon, computed_at.
strategy_state — per-bot resume state: active strategy, position refs, cooldowns, snowball tranche state, DCA grid state.
configs — versioned config with validation schema; active revision pointer; full audit of changes.
risk_events — every breaker/limit/kill action + every AI proposal verdict (append-only).
debriefs — per closed trade: PnL, ATR distances, regime entry vs exit, exit reason, rotation inputs.
4.2 Dialects & migrations
Prod: PostgreSQL 16 + TimescaleDB (hypertables, continuous aggregates, retention). Dev/test: SQLite via the same models. Alembic baseline + forward migrations for both; CI runs migrations on a Postgres-Timescale container to catch drift.
4.3 Backups & recovery
Scheduled pg_dump (daily) + WAL archiving; Redis persistence (RDB + AOF); one-command backup/restore with a restore-drill test in CI; convert-db for SQLite dev → Postgres.
5. Quant engine
5.1 Indicators (Polars)
Spec: TA library (SMA/EMA, RSI, ATR, BBands, MACD, ROC, volume) computed on completed bars only; lookahead-safe by construction (inputs ≤ t-1); optional PyO3/Rust for the heaviest loops [later].
5.2 Regime detector
Spec: classifies TREND_UP / TREND_DOWN / RANGE / HIGH_VOL / LOW_VOL from volatility (ATR percentile) + trend filters; emits RegimeChanged; writes regime_snapshots; gates strategies and the Trade Recycler.
Acceptance: fixture tests — labeled windows classified; boundary cases (flat → trend) tested.

=== PAGE: Business Logic Engines ===
Three pure functions in src/lib/engines.ts. 100% preservation is an acceptance criterion — never make them async, never rename output fields, never add side effects.
calculateRollNesting(input) → RollNestingOutput
Input: wallWidthFt, wallHeightFt, rollWidthInches (42" or 54"), patternRepeatInches
Vertical drops = ceil(wallWidth·12 / rollWidthInches); pattern-matching waste = (drops − 1) · repeatInches
Drop height = wallHeight·12 + 4 (2" bleed top and bottom); continuous meters = linear inches × 0.0254
Required sqft = linearInches · rollWidth / 144; final = max(required, exactWallSqFt · 1.11) — an ≥11% safety buffer is always present
Boundaries tested: 5ft×8ft → 2 drops ≥44.4 sqft · 30ft×15ft → 9 drops ≥499.5 sqft
analyzeSolarLux(input) → SolarLuxOutput
Compass 180°–315° (South→West band) AND floor ≥ 10 → highSolarHeatRadiation: true
Recommendation chain: high heat → Double-cell Honeycomb Blinds; west/SW band only → 100% Blackout Motorized Blinds; else Standard Translucent Sheer
recommendedBlindType is a string-literal union — UI switch statements depend on the exact three values
calculateDynamicPricing(input) → PricingOutput
material = rawMaterialBasePerSqFt · sqft · primer = ₹15/sqft · installation labor = ₹25/sqft
isSmartMotorized adds a flat ₹15,000; GST = 18% of subtotal
Escrow tranches of totalRetailPrice: deposit 10% / material release 60% / post-QA unlock 30%
Invariant tested (R5-B5): deposit10 + materialRelease60 + postQAUnlock30 === totalRetailPrice

=== PAGE: Decisions & Lessons ===
Why these choices, and what we learned from the previous fork + ecosystem research. Updated as decisions land.
Architectural decisions
asyncio single-loop over threads — no GIL fights on the money path; I/O-bound trading fits coroutines
Polars over pandas for live candles — columnar, fast, no index fragility; pandas only in notebooks
PostgreSQL + TimescaleDB over SQLite-only — time-series is the core workload; SQLite retained as dev fallback
Redis Streams over raw pub/sub — consumer groups give replay + at-least-once delivery for zero missed events
Container-per-bot over one mega-process — isolation, canary deploys, horizontal scaling (Hummingbot's 111K-instance model)
Deterministic execution layer — ML/LLM (optional, later) only informs signals/regime; it never executes orders directly
Lessons from the old fork (binance-trade-bot)
Single-file strategy monolith is a dead end → strategy/signal/risk/execution separation
Config-less testnet-first boot is a huge onboarding win → keep .env defaults working out of the box
Look-ahead bias killed prior backtest trust → explicit warm-up + strict prior-bar signal computation
Lessons from ecosystem research
Freqtrade Producer/Consumer: compute analyzed dataframes once, share over websocket → StratForge generalizes with Redis Streams
Freqtrade leverage docs: never 2 bots on one leveraged account; liquidation_buffer formula for stop placement
Hummingbot: bot = container, central API server, executor abstraction with standardized PnL → our worker/control-plane model
Money-path rules (non-negotiable)
Testnet/paper first, always; live requires explicit config flip + safety checks
Stops always attached; adverse-path backtests gate every strategy
Kill switch honored within one loop tick

Debrief feeds the selector: rolling win-rate, expectancy, avg hold time per strategy per regime

=== PAGE: Capital Protection — the 5% Guard ===
User requirement: the bot must never make the user lose more than 5% of the investment. Honest engineering answer: no live system can guarantee a hard cap (gap moves, flash crashes, exchange outages can exceed any stop). StratForge's answer is defense-in-depth: capitalism insurance layered so that exceeding ~5% requires a tail event, and even then the system halts immediately.
The honest truth (design guardrail #0)
Any claim of a guaranteed max loss is false and dangerous. What a serious system does is: (1) make stops tight enough and sizing small enough that normal and adverse paths rarely approach the cap, (2) enforce a hard equity circuit breaker AT the cap so the bot goes flat and stops trading, and (3) keep a reserve/margin so slippage and lags don't push past it. That is what StratForge builds.
Layer 1 — Portfolio equity circuit breaker (the 5% line)
Track portfolio equity continuously (cash + position mark-to-market + margin)
If equity ≤ 100% − 5% of starting equity → HARD STOP: flatten all positions instantly, cancel all orders, stop all strategies, manual disarm required
Demo of layer: loss hits 5% → system flat within one loop tick; logged as risk_events[EQUITY_CIRCUIT_BREAKER]
Layer 2 — Daily loss limit (earlier, softer line)
If day PnL ≤ −2.5% (configurable) → halt NEW entries for the rest of the day; existing positions only defend (stops/trailing)
Prevents one bad day from snowballing toward the 5% cap
Layer 3 — Per-trade & per-strategy risk budgets
Max loss per trade ≤ 1% of equity (ATR-scaled stop) — a string of losses drifts toward daily limit, not the cap
Per-strategy risk budget (e.g., each strategy can spend ≤ 2% before auto-pause + review)
Position sizing = vol-target with hard notional caps; no single position > 5% of equity notionally at liquidation risk
Layer 4 — Exchange-side protection
Exchange stop-loss + take-profit attached at order time on futures; spot uses trailing limit exits
Liquidation-buffer math (Freqtrade formula) keeps our stops safely above the exchange's liquidation price
Layer 5 — Tail-event mitigation
Hard kill switch (file/env): flatten + halt within one tick; honored by every worker
Max leverage cap (default 1x spot, conservative futures) so liquidation risk is bounded
No DCA with martingale multiplier; futures DCA grids capped at 20% at-risk per the Advanced Strategies page
The math that makes 'barely ever exceeds 5%'
Per-trade risk r = 1% equity; daily stop D = 2.5%; equity breaker B = 5%.
Worst-case path to B requires ~5 losing trades in a day OR a single
gap through stops — both guarded by layers 2-4. The 5% breaker is
the backstop, not the plan.
Reporting
Dashboard: live equity drawdown gauge, proximity-to-breaker meter, risk event feed
All breaker/limit hits create risk_events — every protection action is auditable

=== PAGE: Advanced Strategies — Snowball & Futures DCA ===
Two high-value strategies the user asked for, designed safe-first: Position Snowball (add to WINNERS only, ratchet protection) and Futures DCA (bounded averaging-down with hard stops + liquidation buffer). Both are first-class strategies on the signal/risk/execution separation.
Position Snowball (pyramiding)
Concept: build a position in tranches as price moves in your favor, ratcheting protection at each step. This multiplies winners instead of averaging losers.
Mechanics
Entry tranche at signal (N0). Set initial stop-loss + take-profit ladder
Add tranche 1 when price ≥ entry + k1·ATR (e.g. k1=0.8); move stop on the FIRST tranche to breakeven
Add tranche 2 when price ≥ last-add + k2·ATR (k2=0.6); ratchet the whole position's trailing stop up
Take-profit ladder: close 1/3 at +1.5·ATR, 1/3 at +2.5·ATR, remainder trails behind price (iceberg-style exit)
If price reverses between tranches: exit ALL tranches (no averaging down — snowball only adds to winners)
Risk controls (snowball)
Max tranches (default 3), max total exposure = 2× base notional, per-tranche size non-increasing
Only active in TREND_UP / HIGH_VOL regimes with high regime confidence (regime gate)
Stop must not violate liquidation buffer on futures; vol-normalized distances (ATR) not fixed %
Futures DCA (bounded averaging-down)
Concept: enter a position and add at predefined adverse levels to lower average entry, with a take-profit target and a HARD terminal stop. This is grid-like; done unbounded it is martingale (account-killer) — StratForge makes it safe by construction.
Mechanics
Entry at signal price S; adds at S−d1, S−d2, S−d3, S−d4 (d = ATR step, configurable; max_dca_levels default 4)
Size per add: fixed, or multiplier m ≤ 1.0 by default (m > 1 = martingale — requires explicit risk-review opt-in)
Take-profit at avg_entry × (1 + tp_pct), whole-grid close
HARD stop: price ≤ add_level_n − buffer → close everything, no more adds after max_dca_levels
Funding guard: skip adds when |funding rate| > threshold; funding via isolated margin
Risk controls (futures DCA) — mandatory
ISOLATED margin per position; one DCA grid = one position owned by exactly one bot (account-isolation rule)
Total at-risk = Σ notional(all levels) / equity ≤ cap (default 20%)
Liquidation math: recompute liquidation price after every add; enforce stop < liquidation with liquidation_buffer ≥ 0.05 (Freqtrade formula: stop = liq ± |open−liq|×buffer)
Regime gate: entry only in RANGE / HIGH_VOL mean-reversion conditions; no new DCA in TREND_DOWN
Daily-loss circuit breaker + kill switch flattens the whole grid (not one leg)
Backtest gate (both strategies)
Walk-forward + adverse-path stress tests: simulate −30% / −50% drawdown paths; a strategy that fails them cannot be enabled live
Where they live in the architecture
Both implement BaseStrategy.on_candle(); emit Signals with tranche metadata; risk engine enforces the controls above; execution engine manages multi-leg grids as one logical position (position_id)

=== PAGE: Multi-Bot Orchestration ===
Research-backed: Freqtrade Producer/Consumer mode (share computed indicators/signals over a message websocket — compute once, consume everywhere) and Hummingbot (111K+ instances run as isolated containers managed by a central Hummingbot API server). StratForge adopts both patterns: a shared data plane + container-per-bot workers + a control plane.
Goals
Run N bots concurrently: different strategies, different accounts/wallets, different risk profiles, one dashboard
Compute market data + indicators + regime ONCE in a shared data plane; workers only run strategy & risk & execution
Start/stop/inspect any bot without touching others (hot-add strategies, canary-test new strategies)
Architecture — three planes

Data Plane — one MarketDataProducer per (exchange, network): ingests the websocket feed, normalizes, aggregates OHLCV, computes shared indicators + regime; publishes to Redis Streams (consumer groups = reliable, replayable fan-out). Freqtrade-equivalent of producer mode, scaled to Redis
Workers — one isolated process/container per bot. Each subscribes to the data plane, runs its strategy + risk + execution, and reports state (positions, equity, orders, regime) to the control plane. NumPy/Polars heavy signal math stays client-side or is served pre-computed like FreqAI-on-a-powerful-box
Control Plane — StratForge API (FastAPI): register/spawn/stop bots, see per-bot state, aggregated portfolio view, kill switch per bot; supervisor (Docker Compose v2 profiles → Nomad later) restarts on healthcheck failure
Account isolation (critical — from Freqtrade leverage docs)
Never run two bots on the same account with leverage: liquidation math assumes sole ownership of the account (Freqtrade: 'You can't run 2 bots on the same account with leverage'). For futures/leveraged bots StratForge REQUIRES one account per bot (or isolated-margin positions owned by exactly one bot). Spot/margin-free shared accounts are allowed but every bot reconciles its own balances.
Implementation methods (proven in the wild)
Freqtrade Producer/Consumer: analyze on one instance, broadcast analyzed dataframes + whitelist over `external_message_consumer` websocket; consumers reuse without recomputing (see freqtrade.io/en/stable/producer-consumer)
Hummingbot: bot = Docker container ('Bots' = long-running market making/grid); Hummingbot API server centralizes deployment; Condor adds LLM agents observing each bot. Instance count in the 100Ks → design must assume many workers
StratForge adapts: Redis Streams as the message bus (instead of point-to-point websockets) so fan-out is native and replayable; containers per worker for full isolation
Hot-update & canary workflow
A new strategy/version is a new worker: deploy as canary on testnet, observe via dashboard, promote to production by flipping which worker owns the account
Strategy registry in the control plane: strategy_id → image/version → account → risk profile → status

Freqtrade leverage & account isolation: https://www.freqtrade.io/en/stable/leverage/
Hummingbot architecture (client/API/condor): https://docs.hummingbot.org/

=== PAGE: Risk Engine ===
The last gate before orders. If risk rejects, nothing trades — even on a strong strategy signal. Capital preservation is the actual goal; profit is the byproduct.
Pre-trade checks (order of evaluation)
Instrument-level: symbol active, not blacklisted, exchange on testnet/mainnet as configured
Portfolio exposure: per-symbol and per-strategy exposure caps
Size check: order notional within min/max per order, position size ≤ vol-target sizing result
Daily loss limit: if day_pnl ≤ −daily_max_loss_percent → halt new entries (cooldown)
Drawdown circuit breaker: portfolio drawdown from peak ≥ threshold → flat + manual disarm required
Regime guard: in TREND_DOWN / HIGH_VOL, risk multiples shrink and only defensive signals pass
Kill switch: file- or env-triggered (kill.flag) — flattens all positions, cancels orders, stops entries
Risk state
Persisted per day: start-of-day equity, day_pnl, loss cooldown timestamps
risk_events table logs every rejection with reason — dashboard shows a live risk audit trail
Order-level protections
Exchange-side stop-loss + take-profit attached to futures orders where supported
Max slippage guard: execution cancels/rejects if fill price deviates beyond tolerance
Order retry limits and hourly order-count (rate limit) budgets
Liveness & kill
Heartbeats: bot writes heartbeat row; supervisor/healthcheck restarts on stall
kill.flag honored within one loop tick; graceful flatten then process exit
Human override
Manual flat via CLI/API: cancels orders, closes positions, leaves bot paused
Strategy can be disabled per-name without code changes (config or API)

=== PAGE: Strategy Catalogue ===
v1 ships four regime-adaptive strategies selected by the RegimeDetector. 'Profitable in any circumstances' = the ensemble adapts to market regime and risk cuts losses — not a single magic strategy.
v1 strategies
trend_follow — EMA fast/slow cross + ADX strength filter + Donchian breakout confirmation. Favoured in TREND_UP / TREND_DOWN
mean_reversion — Bollinger z-score / RSI extremes mean-reversion within a valid range regime. Favoured in RANGE
momentum — multi-timeframe momentum score (ROC over 1h/4h/1d) + volume confirmation; ranks symbols, enters strongest. Favoured in TREND_UP
vol_breakout — ATR-scaled Donchian breakout with vol filter; captures expansion moves. Favoured in HIGH_VOL
Regime weighting
RegimeDetector outputs (regime, confidence) → strategy weights per regime (table-driven)
Signals weighted by confidence × strategy-regime fit; only the top-weighted signal per symbol moves toward orders
When confidence is low (ambiguous regime), the system defaults to cash/bridge protection (see Risk Engine)
Position & exit logic
Entries: signal + sizing = target order; risk engine validates
Exits: take-profit (ATR multiple), trailing stop, time-based decay, regime flip (de-risk on regime change), stop-loss from risk engine
All exits symmetric for LONG and SHORT on futures; spot is LONG-only for v1 with bridge (quote) as the safe asset
Later phases (design stays open)
Funding-rate arbitrage (futures spot/perp basis)
Pairs / statistical arbitrage (cointegration screening in research notebooks)
Grid / market-making with inventory limits (advanced, gated)
ML regime classification (optional; HMM / gradient-boosted ensemble) as a regime detector variant — never as a black box
Strategy dev workflow
Write strategy in src/stratforge/strategies/, subclass BaseStrategy
Backtest + walk-forward gate in CI (tests/backtests/)
Paper-trade 7+ days on testnet with dashboard monitoring
Promote to live only via explicit config + safety checks
Lessons ported from the fork review
The old bot's bridge-scout (downgrade strong→weak, wait for reversion) is effectively a mean-reversion/pairs idea — it becomes mean_reversion with proper cooldowns
Profit-hunter take-profit concept → take-profit exits in the common exit engine

=== PAGE: Quant Engine ===
Vectorized math on Polars (not pandas). Indicators, regime detection, portfolio sizing and a walk-forward backtester are the same code in research and live — no train/serve drift.
Indicators (quant/indicators.py)
Trend: EMA, MACD, ADX, Donchian channel, linear-regression slope
Mean reversion: RSI, Bollinger Bands, z-score of price vs EMA
Volatility: ATR, realized volatility (percentile-ranked), Hurst exponent (trend vs mean-reverting signature)
Volume: VWAP, volume momentum (OBV), candle-range ratios
All vectorized with Polars expressions; identical signature in research and live pipelines
Regime detection (quant/regime.py)
Multi-factor regime classifier on multiple timeframes. Outputs a regime label + confidence + factor vector, persisted to regime_snapshots:
TREND_UP / TREND_DOWN — EMA alignment + ADX strength + slope sign
RANGE — low ADX, mean-reversion signature (Hurst near 0.5), Bollinger mean reversion
HIGH_VOL — volatility percentile spike (breakout-favourable)
Regime is used to weight strategies and to tilt risk (position size down in adverse regimes)
Signal model
@dataclass
class Signal:
    strategy_id: str
    instrument: Instrument
    side: Side            # LONG / SHORT / FLAT
    strength: float       # 0..1 conviction
    price: Decimal
    meta: dict
Portfolio sizing (quant/portfolio.py)
Volatility targeting — position sized so portfolio vol ≈ target (ATR- or realized-vol based)
Kelly-capped risk fraction (fractional Kelly, configurable cap)
Per-symbol and per-strategy exposure limits enforced downstream by the risk engine
Backtester (quant/backtest.py)
Event-driven replay of stored candles with realistic fee + slippage models
Metrics: CAGR, Sharpe, Sortino, Max Drawdown, Calmar, win rate, profit factor, exposure
Walk-forward validation: train → out-of-sample test windows; strategy activation requires passing the gate
Parameter sanity checks: no look-ahead bias (signals computed strictly on prior bars); warm-up handled explicitly
Strategy base & sandbox
BaseStrategy.on_candle() / on_tick() interfaces; each strategy gets its own persisted state (strategy_state table)
Strategies never touch the broker directly — they emit Signals only
A signal bus merges and weights signals; the risk engine is the last gate before orders
Research notebooks
notebooks/ regime-labelling, indicator validation, strategy lab — Polars + Plotly, reproducible against the DB

Core design principles
Single asyncio event loop — no threads for I/O; flows are coroutines over one loop
Everything is an event: MarketTick, CandleClosed, Signal, RiskRejected, OrderAccepted, OrderFilled… persisted and replayable
Exchange adapters implement typed interfaces (MarketDataProvider, ExecutionProvider) — Binance spot + USDT-M futures in v1, CCXT-ready later
Strategies run isolated (state persisted in DB) and emit signals; the risk engine and portfolio sizing decide whether signals become orders
Paper/simulation mode is a first-class execution provider — same code path as live, zero risk
Layers
Exchange Layer — Binance spot & USDT-margined futures adapters (python-binance 1.0.27 REST + unicorn WS stack, adapted for async)
Data Layer — websocket feed, OHLCV aggregation (1s→1m→5m→15m→1h→4h→1d), historical backfill, time-series store
Quant Engine — indicators, regime detection, strategy manager, signal bus, portfolio sizing
Risk Engine — pre-trade checks, limits, circuit breakers, kill switch
Execution Engine — order lifecycle, fill detection, retry/cancel, reconciliation against exchange
Application Layer — FastAPI REST, WebSocket live updates, CLI, metrics
Key flows
Feed: WS ticker/candle → normalize → persist → broadcast CandleClosed on aggregation boundaries
Signal: on each completed candle, strategies compute → RegimeDetector weights → winning strategy emits Signal(s)
Gate: RiskEngine validates size/limits/exposure → approve or reject → ExecutionEngine places order
Reconcile: periodic + post-fill reconciliation reconciles local positions vs exchange, writes position/equity snapshots
Dashboard: FastAPI serves REST + WS stream of candles, equity, regime, positions, orders
Dependency & config
uv for dependency management (uv.lock, fully pinned). Pydantic-settings for config: defaults → .env → env vars → config DB table. Multi-mode: research (offline), paper (simulated), live (testnet), live (mainnet, explicit opt-in with safety gates).

=== PAGE: Risk Management ===
A safety layer added in Phase 2: hard stop-loss + trailing stop + cooldown, tracked per-coin in the CoinState model.
CoinState tracking
models/coin_state.py stores per-coin: buy_price, peak_price, stop_loss_hit_at. It is written at entry (transaction_through_bridge) and updated every scout cycle. The current coin's state is the source of truth for risk decisions.
check_stop_loss()
Runs every scout cycle for the current holding
Hard stop: if price ≤ buy_price × (1 − stop_loss_percent/100) → sell to bridge, record stop_loss_hit_at
Trailing stop: peak_price tracks the highest price since entry; if price ≤ peak_price × (1 − trailing_stop_percent/100) → sell to bridge, record stop_loss_hit_at
Cooldown: if stop_loss_hit_at is recent (< stop_loss_cooldown_hours), the same coin is not re-entered, preventing stop-loss death spirals
Configuration
stop_loss_percent — hard stop, 0 disables (default 0)
trailing_stop_percent — trailing stop, 0 disables (default 0)
stop_loss_cooldown_hours — re-entry cooldown (default 12)
Design notes
Stop-loss exits always go through the bridge (coin → bridge), so funds are never stuck in a halted pair
The improved bridge_scout picks the most-undervalued coin (not the first match), and skips coins in stop-loss cooldown
Testnet-first by default means you can rehearse all of this with zero real funds

=== PAGE: Trading Strategies ===
Strategies subclass AutoTrader and override scout(). Discovered automatically: any file named *_strategy.py in strategies/ is loaded; its class must be named Strategy.
How to write a strategy
from binance_trade_bot.auto_trader import AutoTrader

class Strategy(AutoTrader):
    def scout(self):
        # your logic here
        pass
Then set strategy=<name> (file prefix before _strategy). In a subfolder works too.
default
The classic core loop. Each cycle it compares the current coin against all pairs to the bridge; when another coin is significantly undervalued relative to the current one (past the scout threshold), it jumps into that coin through the bridge. Semantics: the bot downgrades strong→weak, buying the cheaper/weaker coin and waiting for price reversion.
multiple_coins
Same core logic, but the bot does not require a single global current coin — it can hold and manage multiple coins, making it less likely to get stuck when one coin is untradeable or halted.
momentum (new)
Adds a momentum edge to the jump decision. Computes a momentum_score over momentum_window candles (see indicators.py) for candidate coins; only jumps when the cheaper coin also has positive momentum, filtering out falling-knife entries. Tune with momentum_window.
rsi (new)
Mean-reversion RSI gating. Uses rsi_period; treats RSI ≤ rsi_oversold as a buy region and RSI ≥ rsi_overbought as a sell region. The jump logic is gated so the bot buys weakness (oversold) and takes profit/sells strength (overbought).
Planned: profit_hunter
Port of the profit-hunter take-profit concept from the ajayspi/CEX option-futures quant bot review. Adds a profit_hunter_target knob: when the current coin reaches buy_price × (1 + target%), sell to the bridge to bank profit, then re-enter via the improved bridge_scout. Downside protection reuses the existing check_stop_loss layer. Status: in development.
Strategy semantics — important!
This bot jumps INTO the weaker/cheaper coin when the margin turns favorable, waiting for mean reversion. Momentum and RSI strategies gate that jump with indicators — they do not flip the direction. Tests encode this behavior (test_default_strategy_jumps_to_weakest_coin, test_default_strategy_stays_when_other_coin_rallies).

=== PAGE: Architecture ===
Single-process Python app: scheduler → AutoTrader (strategy) → Binance API manager (+ websocket stream) → SQLite DB → optional Flask-SocketIO dashboard API.

Data flow
Scheduler wakes AutoTrader.scout() every scout_sleep_time seconds
scout() pulls ticker prices for supported coins vs bridge, computes margins against current holding
Strategy decides to jump/swap (downgrade strong→weak logic: enter the undervalued/weaker coin, wait for reversion)
transaction_through_bridge() executes order pair via bridge (e.g. COIN→USDT→NEWCOIN), records CoinState (buy price, peak price)
check_stop_loss() runs each cycle — hard stop + trailing stop, with cooldown flagging in CoinState
Every action is written to SQLite (trades, scout history, coin values) and mirrored to the dashboard via SocketIO
Key design decisions
SQLAlchemy upgraded to 2.0.54 with 1.x-isms fixed (select([...]) → select(...), session.get(), declarative_base from sqlalchemy.orm)
eventlet dropped → Flask-SocketIO simple-websocket threading mode (eventlet is deprecated/bugfix-only)
websocket client bumped to unicorn-binance-websocket-api 2.16.1 for Binance's Feb 2026 userData WS change
Strategies auto-discovered by filename (*_strategy.py); class must be named Strategy and subclass AutoTrader

=== PAGE: Getting Started ===
Local Windows dev environment: Python 3.12.10. The verified venv is .venv-test with all pinned deps installed.
Prerequisites
Python 3.12+ installed and on PATH
A Binance testnet account if you want live feed testing (optional for the default flow)
Internet access to api.binance.com (REST) and stream.binance.com (websocket)
Install
Clone or use the working tree at C:\Users\vigilare\Trading bot
Create and activate a virtual environment:
python -m venv .venv-test
.venv-test\Scripts\activate
Install pinned dependencies:
pip install -r requirements.txt
pip install -r dev-requirements.txt   # for tests/lint
Run the bot (testnet-first)
No configuration file is required — the bot boots on sane defaults in testnet mode:
python -m binance_trade_bot
To run with a config file, copy .user.cfg.example to user.cfg, edit the values (bridge, strategy, stop-loss knobs…), then run the same command. LIVE TRADING only happens when you set testnet=false AND provide real API keys — do not do that until you understand the risk rules in Risk Management.
Run the API / dashboard server
python -m binance_trade_bot.api_server
# default http://localhost:5123
Run the test suite
.venv-test\Scripts\python.exe -m pytest tests -q   # 30 tests, all green
Environment variables (override user.cfg)
Every setting can also be set via env var: BRIDGE_SYMBOL, TESTNET, API_KEY, API_SECRET_KEY, TLD, SUPPORTED_COIN_LIST, CURRENT_COIN_SYMBOL, STRATEGY, SELL_TIMEOUT, BUY_TIMEOUT, USE_MARGIN, SCOUT_MULTIPLIER, SCOUT_MARGIN, SCOUT_SLEEP_TIME, HOURS_TO_KEEP_SCOUTING_HISTORY, STOP_LOSS_PERCENT, TRAILING_STOP_PERCENT, STOP_LOSS_COOLDOWN_HOURS, MOMENTUM_WINDOW, RSI_PERIOD, RSI_OVERSOLD, RSI_OVERBOUGHT.
Environment variables win over user.cfg. SUPPORTED_COIN_LIST can also be supplied via a supported_coin_list file (one coin per line, # comments allowed).

=== PAGE: Project Overview ===
Modernized binance-trade-bot: runs on Python 3.12 / 2026 tooling, ships new profitable strategies and a modern dashboard. Testnet-first by default.
What this is
This is a fully modernized fork of ajayspi/binance-trade-bot (itself a fork of the well-known ccxt-trade-bot). The project was cloned, brought up to date for Python 3.12 and 2026-era dependencies, extended with new trading strategies and a risk-management layer, and is gaining a modern web dashboard.
Goals
Run cleanly on current 2026 tooling (Python 3.12, SQLAlchemy 2.0, Flask 3, current websocket stack)
Add genuinely profitable strategy logic on top of the core bridge-scout loop
Ship the modern dashboard the project was missing
Stay testnet-first and safe: no live keys required to run, tests never touch real balances
Current status
Phase 1 (2026 readiness): DONE — dependencies, SQLAlchemy 2.0 fixes, config defaults, API fixes
Phase 2 (strategies + risk): DONE — momentum & RSI strategies, stop-loss/trailing-stop layer, improved bridge_scout
Phase 3 (dashboard): IN PROGRESS — templates, static assets, live SocketIO updates
Phase 4 (tests & docs): PARTIAL — 30 pytest cases green; docs now maintained in Notion
Key facts
Python 3.12.10 • REST via python-binance 1.0.27 • SQLAlchemy 2.0.54
WebSocket streaming via unicorn-binance-websocket-api 2.16.1 (handles Binance's Feb 2026 userData WS change)
Flask-SocketIO runs in simple-websocket threading mode (eventlet dropped — it is deprecated/bugfix-only)
No user.cfg required: app boots on defaults in testnet mode out of the box
